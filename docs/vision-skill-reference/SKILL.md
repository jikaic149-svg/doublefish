# Vision

把训练、视觉推理/跟踪和设备视觉应用视为三个边界清晰的工作面。先选择工作面，再读取对应参考；不要因为用户提到 YOLO 就自动推断需要部署到设备。

## 路由

| 用户目标 | 必读参考 | 交付边界 |
|---|---|---|
| 整理素材、抽帧、标注、划分、训练、验证或 `.pt` 推理 | `references/pt-training.md` | `best.pt`、`last.pt`、指标和预测预览 |
| 实时图片/视频检测、ROI 跟踪、多目标关联、结果融合或可视化 | `references/realtime-vision.md` | 结构化检测/轨迹结果、预览和性能评估 |
| 在 MaixCAM 系列设备上开发、运行或调试 MaixPy/MaixCDK 视觉应用 | `references/maixpy-device.md` | 真机视觉代码、运行日志和调试图片 |

组合任务按“数据与训练 → 视觉推理/跟踪 → 设备验证”的顺序处理，但保持每一层的输入、输出和验证独立。

## 开始前

1. 检查当前项目结构、现有配置、权重、脚本和未提交改动。
2. 明确当前任务属于哪个工作面；只有跨层目标才加载多份参考。
3. 从本地文件和可执行程序发现版本与路径，不沿用源 skill 中的旧绝对路径。
4. 明确模型类型、类别顺序、输入尺寸、数据来源和最终运行平台。
5. 采用最接近真实使用方式的本地验证；需要硬件时，明确区分本地检查和真机验证。

## 边界规则

- 默认模型交付物只包含 PyTorch `.pt`。不要安装或引入 ONNX、MUD、AXModel、Pulsar2、量化或校准流程。
- 不要声称普通 Ultralytics `.pt` 可以直接在 MaixPy/KPU 上运行。训练产物和设备运行时之间没有经过验证的桥接时，保持两条链路分离。
- 不要继承 MaixCAM2 专用的采集分辨率、编码器故障、默认密码或性能假设；先识别实际设备。
- 不要把模型与标签的一致性当作泛化能力。最终结论必须来自独立验证/测试数据和真实场景预览。
- 视觉 skill 的边界止于结构化视觉结果，例如类别、边界框、掩码、关键点、轨迹 ID、中心、速度、置信度和有效性。不要设计外部设备或非视觉业务接口。
- 不要把密码写入聊天、命令参数、代码、日志或总结。

## 数据与产物规则

- 保持原始素材只读，把已审核 YOLO 图片/标签作为数据真源，把划分清单和运行结果视为可重建产物。
- 固定类别 ID；标注开始后不得重排类别。
- 按视频、场景或采集批次划分数据，避免相邻帧泄漏到不同集合。
- 让每次实验自包含配置、权重、指标和预测结果，禁止多个项目共用可写训练输出目录。
- 自动标注、传统视觉候选框和视觉模型建议只能进入待复查区，不得默认覆盖可信人工标签。

## 实现与验证

- 优先复用项目现有工具；项目专用脚本放在项目内，可跨项目复用的工具放仓库级 `tools/`。
- 对数据任务检查图片-标签配对、坐标合法性、类别范围、重复数据和分组泄漏。
- 对训练任务至少检查训练是否完成、`best.pt` 是否可加载、独立集指标和预测预览。
- 对实时视觉任务使用带时间戳、来源、有效性和状态的结构化结果，并生成可复查的图像、视频或指标。
- 对 MaixPy 应用提供显式退出路径，最终代码关闭调试图片，并使用 MaixPy 显示 API 而不是 `/dev/fb*`。
- 最终说明已生成的产物、执行过的验证、未验证的硬件环节和仍存在的限制。
